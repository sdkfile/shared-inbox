# 사람과 AI 의 분담

이 문서는 코드보다 설계에 관한 것이다. 라이브러리는 경계를 표현할 뿐,
지키는 건 만드는 사람이다.

## 기준 하나

> **사람이 자동화를 꺼도 업무가 그대로 돌아가야 한다.**

이 문장 하나로 대부분의 설계 판단이 갈린다.

- AI 가 읽음 표시를 한다 → 끄면 사람이 뭘 봤는지 모른다 → **안 된다**
- AI 가 라벨을 옮긴다 → 끄면 분류가 사라진다 → **안 된다**
- AI 가 초안을 옆에 붙인다 → 끄면 초안만 없다 → **된다**

## 왜 "AI 가 처리하기" 가 실패하는가

```
1주차   AI 가 90% 를 정확히 처리한다. 사람은 감탄한다.
2주차   사람이 대충 훑는다. 거의 맞으니까.
4주차   사람이 안 본다.
6주차   AI 가 중요한 걸 하나 놓친다. 아무도 몰랐다.
7주차   사람이 전부 다시 읽기 시작한다. 자동화는 켜져 있지만 아무도 안 본다.
```

정확도가 문제가 아니다. **90% 정확한 자동화는 100% 신뢰를 얻거나 0% 를 얻는다.**
중간이 없다.

그래서 사람이 계속 읽게 만드는 쪽을 택한다. AI 는 읽는 속도를 올려주는 도구지
읽기를 대신하는 도구가 아니다.

## 승인 화면에 담을 것

```
┌────────────────────────────────────────────┐
│ 견적 문의 — 김담당 <manager@client.co.kr>   │
├────────────────────────────────────────────┤
│ 판단   사람 확인 필요 (신규 문의)           │
│ 근거   과거 거래 없음, 금액 언급 있음        │
│                                            │
│ ⚠ 확인하세요                                │
│   "표준 계약서 양식이 있습니다"              │
│   → 그런 양식이 없습니다                    │
│                                            │
│ ── 초안 ──────────────────────────────     │
│ 안녕하세요, 문의 감사합니다...              │
│                                            │
│ [보내기]  [고쳐서 보내기]  [보류]           │
└────────────────────────────────────────────┘
```

**반드시 있어야 하는 것:**

| 항목 | 이유 |
|---|---|
| 판단 근거 | 사람이 뒤집으려면 왜 그렇게 판단했는지 알아야 한다 |
| 경고 | 지어낸 사실은 사람이 그냥 읽으면 안 걸린다 |
| 원문 링크 | 요약만 보고 판단하면 요약의 오류를 물려받는다 |
| "고쳐서 보내기" | 이게 없으면 초안이 틀렸을 때 처음부터 다시 쓴다 |

**넣지 말 것:**

- 확신도를 통과 기준처럼 보이게 하는 것 (`98% 확신` → 사람이 그냥 누른다)
- 자동 발송 타이머 (`30초 후 발송됩니다`)
- 판단 근거 없는 결론

## 확신도를 믿지 마라

실측 기록이다. 같은 사업자등록증 이미지, 같은 프롬프트.

| 모델 | 읽은 상호 | 확신도 |
|---|---|---|
| gpt-4o | 별오디스튜디오 | 0.95 |
| gpt-4.1 | 별오디스튜디오 | **0.99** |
| gpt-5.2 | 빌포인터스튜디오 | 0.98 |

정답은 **널포인터스튜디오**. 셋 다 틀렸고 확신도는 전부 높았다.

확신도가 정확도와 상관없다는 걸 보여주는 사례라, 우리는 두 가지를 했다.

1. 카드에 확신도를 띄우되 **"참고용"** 이라고 명시
2. 대조 가능한 값(사업자등록번호는 체크섬이 있다)으로 DB 를 조회하고,
   상호는 **판독값과 DB 값을 나란히** 보여줌

```ts
// 판독값으로 DB 를 덮어쓰지 않는다
if (extracted.businessNumber === known.businessNumber) {
  // 번호가 맞으면 상호는 DB 것을 쓴다. 판독값은 경고로만 표시.
  return { ...known, warning: `판독: ${extracted.name} / 등록: ${known.name}` }
}
```

## 지어낸 사실 잡기

`checkClaims()` 는 정규식이다. LLM 으로 LLM 을 검사하지 않는 이유는
그러면 검사기도 지어내기 때문이다.

```ts
checkClaims(draft.body, {
  rules: [
    ...COMMON_RULES,
    // 우리 팀에 없는 것들을 나열한다
    { pattern: /표준\s*계약서[^.\n]{0,12}(있|보유)/, reason: '계약서 양식이 없습니다' },
    { pattern: /(경쟁사|독점)[^.\n]{0,20}(가능|보장)/, reason: '독점 기준이 없습니다' },
  ],
  urls: [
    // 정확해야 하는 링크
    { domain: 'drive.google.com', canonical: MEDIA_KIT_URL },
  ],
})
```

### 유보 표현은 봐준다

```
"표준 계약서 양식이 있습니다"                    → 잡는다
"표준 계약서 양식이 있는지 확인 후 안내드릴게요"  → 넘어간다
```

두 번째는 정직한 답이다. 이걸 잡으면 오탐이 되고, **오탐이 잦으면 사람이
경고 자체를 무시한다.** 그게 경고가 없는 것보다 나쁘다.

### 새 자산이 생기면 규칙을 지운다

미디어킷이 실제로 만들어진 날, "미디어킷이 없습니다" 규칙을 지웠다.
규칙을 안 지우면 정상 답신에 경고가 뜨고, 위와 같은 문제가 생긴다.

## 발송은 코드로 막지 않는다

이 패키지에 발송 함수가 없는 건 방어가 아니라 **설계 표현**이다.
쓰는 쪽에서 `resend.emails.send()` 를 부르면 그만이다.

진짜 방어는 이렇게 한다.

```ts
// 승인 토큰 없이는 발송 함수를 부를 수 없게
async function sendReply(draftId: string, approval: ApprovalToken) {
  const draft = await db.draft.findUnique({ where: { id: draftId } })

  // 승인자가 사람인지, 이 초안에 대한 승인인지 확인
  if (approval.draftId !== draftId) throw new Error('승인 대상이 다릅니다')
  if (!approval.approvedBy) throw new Error('승인자가 없습니다')

  // 승인 후 초안이 바뀌었으면 거절 — 승인한 내용과 나가는 내용이 달라진다
  if (draft.updatedAt > approval.approvedAt) {
    throw new Error('승인 후 초안이 변경되었습니다')
  }

  await resend.emails.send({ ... })
}
```

마지막 검사가 중요하다. 승인 화면에서 본 내용과 실제 나가는 내용이 같아야
승인에 의미가 있다.

## 자기 메일 차단

자동화가 자기가 보낸 메일에 반응하면 무한 루프다.

```ts
const OWN = ['support@example.com', 'billing@example.com', 'noreply@example.com']

if (isSelfAddressed(email.fromAddress, OWN)) {
  await markProcessed(row.id, { reason: 'self_addressed' })
  return
}
```

별칭까지 전부 넣어라. 우리는 운영 계정 3개가 서로 메일을 주고받는 구조라
빠뜨린 하나에서 사고가 났다.
